## 2026-05-01 — SEO при hash-маршрутизации SPA — Active

- **Решение:** Канонический URL для каждого виртуального раздела задавать как **`{SITE_ORIGIN}/#{route}`** (например `https://voensovet.ru/#help`). Базовый домен по умолчанию **`https://voensovet.ru`**, переопределение через **`VITE_SITE_URL`**. Публичные **`robots.txt`** и **`sitemap.xml`** лежат в **`public/`** и попадают в **`dist/`** при сборке; личный кабинет, админка и OAuth callback помечены **`noindex`** в **`SEO_BY_PAGE`**.
- **Причина:** Приложение на клиентском hash без History API; единый `title`/meta задаются компонентом **`AppRouteSEO`** по ключу страницы из **`routeSeo.ts`**.

## 2026-11-26 — Прототип проводника без неподтверждённых мер — Active

- **Решение:** Создать отдельный адаптивный экран `#navigator` на существующем React-стеке. Пока данные о мерах не проверены, показывать только демонстрационные сценарии с явной пометкой; не выдавать их за права, льготы или действующие программы. Страница помечена `noindex`.
- **Причина:** Показать путь пользователя и региональную фильтрацию для пилота 33/40 без публикации недостоверной правовой и социальной информации. Вопрос классифицируется локально, без существующего внешнего AI-маршрута.

## 2026-11-26 — Целевая модель данных проводника — Active

- **Решение:** Для рабочего MVP хранить анкету и историю маршрута на сервере приложения. Каталог мер должен иметь федеральный или региональный охват, условия применимости, источник, дату проверки, документы, ведомство, способ обращения и сроки. Публикацию допускать после редакционной проверки.
- **Причина:** Подтверждённые требования владельца продукта и необходимость воспроизводимого, проверяемого пути. Реализация серверной модели и механизма публикации ещё впереди.

## 2026-11-26 — Регион по профилю и управляемый список — Active

- **Решение:** Регион для маршрута берётся из ручного выбора пользователя и хранится в `users.region_id`; IP-определение удалено. Доступные для нового выбора регионы хранятся в `admin_settings.enabled_regions`, по умолчанию 33 и 40; администратор меняет их в отдельной вкладке существующей админки. Включение региона не публикует меры автоматически.
- **Причина:** Пользователь может физически находиться вне региона проживания; необходим стабильный выбор при работе с другого устройства и управляемый пилотный охват.

## 2026-11-26 — Целевые группы первого релиза — Active

- **Решение:** В первый релиз персонального маршрута включить ветеранов с удостоверением, участников в процессе оформления статуса, членов семей и семьи погибших. Отсутствие готового удостоверения само по себе не должно скрывать все меры. Применимость определяется условиями каждой проверенной меры и статусом документов пользователя.
- **Причина:** Уточнение владельца продукта; помощь нужна и во время оформления статуса, и семьям. Группа используется для предварительного отбора проверенных карточек; окончательная применимость зависит от условий меры.

## 2026-11-26 — Проверенные механизмы дома и своего дела — Active

- **Решение:** В прототипе отдельно показывать соцконтракт на предпринимательство, целевой сертификат многодетной семье во Владимирской области, земельный участок для отдельных участников СВО и семей погибших в Калужской области и выплату вместо участка в городе Калуге. Каждая карточка содержит официальный источник, дату проверки, условия, документы и шаги. Не объединять их под обещанием универсальной субсидии на строительство или открытие бизнеса.
- **Причина:** У этих механизмов разные основания и география; неверное обобщение создаёт ложное ожидание выплаты. До серверного каталога проверенные карточки хранятся в локальном массиве прототипа.

## 2026-11-26 — Граница передачи данных внешнему AI — Active

- **Решение:** Перед внешним AI заменять свободный вопрос на заранее заданную общую формулировку по локально определённой теме. Не передавать ID учётной записи, ФИО, контакты и регион, присланный клиентом; использовать случайный ID обращения и регион из серверного профиля. Удалить Метрику с записью действий и содержимое персональных запросов из логов. Сохранить историю исходных вопросов на сервере приложения.
- **Причина:** Свободный текст может содержать любые персональные сведения; удаление только известных форматов не гарантирует обезличивание. Общий ответ AI имеет меньшую точность, что явно указано в интерфейсе. Персональный маршрут будет работать по проверенному каталогу мер на сервере приложения.

## 2026-11-26 — Редактируемый каталог мер и публикация — Active

- **Решение:** Хранить меры в PostgreSQL как черновики или опубликованные карточки. Публикацию выполнять отдельным администраторским действием после проверки обязательных полей и официального источника; любое редактирование опубликованной карточки снимает её с публикации. Публичный API выдаёт только опубликованные записи, фильтруя по субъекту РФ и при необходимости населённому пункту.
- **Причина:** Нужна редакционная проверка и воспроизводимый источник для каждой рекомендации. Городские меры нельзя автоматически показывать всем жителям области. Прототип проводника подключается к каталогу после наполнения данными.

## 2026-11-26 — Начальное наполнение и срок действия мер — Active

- **Решение:** Загрузить десять проверенных начальных карточек при инициализации БД по уникальному `source_key` без перезаписи редакторских изменений. Проводник использует только опубликованные записи сервера; при отказе API показывает лишь демонстрационные сценарии. `date_end` скрывает завершившуюся меру из публичной выдачи; админские фильтры выделяют новые, истёкшие и не проверенные более 90 дней меры.
- **Причина:** Устаревшая информация не должна продолжать показываться из локального резерва. Дата окончания и дата перепроверки источника решают разные задачи; автоматическое отслеживание изменений на сайтах ведомств пока не реализовано.

## 2026-11-26 — Минимальная анкета и объяснимый подбор — Active

- **Решение:** Хранить признаки анкеты отдельно от контактов пользователя в `navigator_profiles`, доступной только владельцу через авторизованный API. Регион подбора брать исключительно из `users.region_id`. В каталоге хранить редактируемые ограниченные `match_rules`; движок исключает лишь карточки с явным несовпадением проверяемых условий, а оставшиеся условия показывает как требующие проверки. Свободный вопрос не отправлять на сервер подбора.
- **Причина:** Первичный маршрут должен быть воспроизводимым и понятным без передачи лишних персональных данных. Анкета не содержит достаточно сведений для юридического решения о назначении поддержки.

## 2026-11-26 — Сохранённые маршруты и версии шагов — Active

- **Решение:** Хранить выбранные меры и отметки шагов в отдельных таблицах по `user_id`. Отметку связывать с номером и содержимым текущего шага; при изменении текста или порядка старая отметка не применяется к новой инструкции. Сохранённые меры после истечения срока, снятия с публикации, смены региона или анкеты оставлять видимыми, но запрещать новые отметки. Удаление маршрута каскадно удаляет его отметки.
- **Причина:** Пользователь должен продолжать путь на другом устройстве, видеть ранее выбранные меры и не воспринимать устаревшую инструкцию как выполненную. Отметки отражают действия пользователя, а не подтверждённое ведомством право.

## 2026-11-26 — Конфигурация и возврат Yandex OAuth — Active

- **Решение:** Перед перенаправлением к Яндексу требовать OAuth ID, секрет, callback URI и адрес фронтенда. Передавать параметры авторизации через `URLSearchParams`; токен после callback направлять во фрагмент `#auth-callback` приложения и удалять его из адресной строки после чтения. При ошибке возвращать пользователя на экран с сообщением.
- **Причина:** В рабочем API был пустой `client_id`, а прежний callback использовал путь, который не соответствует hash-маршрутизации SPA. Значения OAuth хранятся в окружении Coolify, а не в исходном коде.

## 2026-11-26 — Сохранение маршрута ошибки OAuth — Active

- **Решение:** При первом монтировании SPA брать маршрут из адреса один раз; далее реагировать только на события изменения hash. На ошибке OAuth оставлять `#auth-callback?error=...`, а при успешном входе заменять фрагмент с токеном на `#profile`. В API фиксировать стадию и код сбоя без секретов.
- **Причина:** При полной загрузке callback дочерний компонент удалял hash раньше, чем родительский обработчик прочитывал его, и ошибка скрывалась за главной страницей. Диагностика нужна для определения отдельной причины сбоя обмена токеном или сохранения пользователя.
